# 프로젝트별 가드레일

출처: GitHub 이슈 JunjaK/ai-harness#1 (2026-09-23). 이 문서는 요청과 제약만 기록한다. 설계는 spec에 있다.

## 문제

브랜치·배포 규약과 금지 명령이 CLAUDE.md와 memory에 텍스트로만 있어서, 에이전트가 규칙을 알고도 같은 사고를 반복한다. 한 회사 프로젝트에서 측정한 횟수:

- 운영(main) 머지 금지인데 에이전트가 머지: 3회
- 커밋 전에 브랜치를 확인하지 않아 보호 브랜치(stage)에 직접 커밋·push·자동 배포: 9회. 9번째는 브랜치를 출력해 놓고 `&&`로 커밋을 이어 붙인 경우였다.
- 금지된 전체 테스트 실행으로 개발 PC 정지: 3회

플러그인 훅에는 Bash 명령을 검사하는 `PreToolUse`가 없다.

## 원하는 결과

- 보호 브랜치에 대한 커밋·push·PR 머지를 기계적으로 막거나 사람 확인을 요구한다.
- 규약은 프로젝트마다 다르다. 하드코딩하지 않고 프로젝트별 설정으로 둔다. 토이 프로젝트는 제약이 없고, 회사 프로젝트는 main 금지 + stage/dev 확인이다.
- 서브모듈마다 규칙이 다를 수 있다. 예: BE만 main 머지가 곧 운영 배포.
- `/team-run`처럼 사람이 보고 있지 않은 자동 실행에서도 막혀야 한다.

## 제약

- 설정 파일이 없는 프로젝트는 동작이 전혀 바뀌지 않는다.
- 브랜치와 무관한 금지 명령은 Claude Code 기본 권한 규칙(`permissions.deny`)에 둔다. 기본 규칙이 이미 체인·서브셸을 나눠 검사하므로 훅으로 다시 만들지 않는다.
- Codex도 지원할 예정이다. Claude 쪽을 먼저 끝내고 Codex를 이어서 구현한다. Codex는 `ask`를 지원하지 않고 기본 규칙이 샌드박스 안 명령에 적용되지 않으므로, 그때 평가기를 공유하는 구조로 확장한다.

## 비목표

- 의도적인 우회(스크립트 파일 생성 후 실행, 에일리어스) 차단. 목표는 실수로 생기는 사고다.
- 서버 쪽 브랜치 보호(GitHub branch protection) 대체.
- 이번 단계의 규약 생성 커맨드, `/team-init` 연동, Codex 훅. 모두 후속 단계다.

## 추가 요청 (2026-09-23, 설계 검토 중)

- 가드레일 설정은 **유도하되 의무가 아니다**. 설정하지 않은 프로젝트도 그대로 동작해야 한다.
- **기본 정책은 운영(prd) 브랜치 deny, 나머지 공유 브랜치 ask**다.

## 열린 질문

- Windows Git Bash에서의 동작은 회사 PC에서 테스트 러너로 확인해야 한다.
